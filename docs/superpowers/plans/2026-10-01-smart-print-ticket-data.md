# Smart Print Ticket Data Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Send `dataFormatESCPOS`, `dataFormatXML`, and versioned `ticketData` from the POS frontend to SmartEat Printer Agent, then let each Printer Agent printer choose between the received ESC/POS ticket and a reconstruction from `ticketData`.

**Architecture:** The POS frontend remains the source for direct print payloads and builds both the existing device payloads and a structured `ticketData` contract. The Printer Agent stores a `ticketSource` setting per printer, defaults existing printers to `received`, and routes either the received ESC/POS bytes or a transport-compatible rendering generated from `ticketData.render`. The backend cloud printing flow is intentionally unchanged.

**Tech Stack:** Nuxt 2/Vue 2 frontend helpers and Node tests in `pos-app`; Electron/Node/Vue 3 Printer Agent with Node test runner in `printing-app`.

**Spec:** `C:/Users/kalag/Desktop/projects/clone-pos/pos/pos-app/docs/superpowers/specs/2026-10-01-smart-print-ticket-data-design.md`

## Global Constraints

- Direct frontend to Printer Agent only; do not modify Express `/pushprintingjob` or `/pullprintingjob`.
- Do not change the ESC/POS ticket output generated by the frontend.
- Every direct `/print` payload from the frontend must include `dataFormatESCPOS`, `dataFormatXML`, and `ticketData`.
- Existing Printer Agent printers default to `ticketSource: "received"`.
- In `received` mode, Printer Agent uses `dataFormatESCPOS` even when XML and `ticketData` are present.
- In `ticketData` mode, `ticketData.render` is the print source of truth.
- `ticketData.business` is retained for debug/history/future use and does not override `render`.
- History/PDF prefer the reconstructed `ticketData` view when available.
- Unsupported reconstruction transports are skipped silently; if no compatible transport remains, the job fails clearly.
- Cashier legal replacement text applies only inside Printer Agent reconstruction, not frontend ESC/POS.

## Review Focus

- Cashier legal fields absent from shop settings must not change frontend ESC/POS, but must render replacement labels when Printer Agent reconstructs.
- Existing saved Printer Agent configurations without `ticketSource` must migrate to `received` and continue printing received ESC/POS.
- Mixed printer setups must allow one printer to use `received` and another to use `ticketData` for the same job.
- A `ticketData` printer with missing or invalid `ticketData` must fail with a clear error instead of silently falling back to received ESC/POS.
- History/PDF must show the reconstructed ticket while still exposing the full payload JSON for diagnosis.
